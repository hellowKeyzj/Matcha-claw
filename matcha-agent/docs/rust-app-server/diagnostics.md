# 诊断与错误约束

本文面向后续并行开发 agents，是 Rust app-server 的目标约束，不表示已经实现或完成运行验证。
前提已定：独立、轻量、模块化 Rust 服务；CLI 初期不改，仅作执行后端；支持高并发、多 CLI 会话。
代码精简不等于错误简化：所有真实异常分支、具体返回与恢复/清理结果必须从首次实现就完整可追踪。
不为未发生的需求添加防御、任意限制或泛化状态机；真实失败边界不能以“后续补诊断”为由省略。
共享入口见 [README](README.md)；架构与运行布局分别由 [architecture](architecture.md)、[runtime-layout](runtime-layout.md) 定义。
协议执行、能力范围、开发流程分别见 [protocol-execution](protocol-execution.md)、[capabilities](capabilities.md)、[development](development.md)；本文不重复定义这些 owner 的契约。

## 事实入口与未观测边界

- [编码宪法](../../../CODING_CONSTITUTION.md) §2、§9、§11、§16–18：状态显式、取消清理、历史事件不覆盖、领域错误自治、错误可行动、诊断先脱敏。
- [Rust 实现规范](../../../RUNTIME_HOST_TS_RUST_IMPLEMENTATION_STANDARD.md) §1、§2.2、§3.3、§4：事实/机制/投影分离，资源与错误归各自边界，显式可失败清理。
- [`print.ts:2933–2958`](../../src/cli/print.ts#L2933)：原生 `control_response` 按 `request_id` 回答，区分 `success` 与携带字符串 `error` 的失败。
- [`print.ts:3038–3069`](../../src/cli/print.ts#L3038)：`interrupt` / `end_session` 发出 abort 后返回成功 response；这不是执行或清理完成证明。
- [`print.ts:948–996`](../../src/cli/print.ts#L948)：结果区分执行失败、max turns、budget、structured-output retries；最终退出码还依赖 `is_error`。
- [`print.ts:2536–2563`](../../src/cli/print.ts#L2536)：执行异常尝试发出 `error_during_execution`；写出失败仍可能直接进入退出路径。
- [`print.ts:580–637`](../../src/cli/print.ts#L580)：部分参数/沙箱启动失败仅写 stderr 后退出，不能假定总有结构化错误结果。
- [`structuredIO.ts:252–264`](../../src/cli/structuredIO.ts#L252)、[347–486](../../src/cli/structuredIO.ts#L347)、[493–558](../../src/cli/structuredIO.ts#L493)：EOF 拒绝 pending request；response 有错误、schema 校验、重复/孤儿分支；发送支持取消并清理 pending。
- [`print.ts:3298–3344`](../../src/cli/print.ts#L3298)：reload 已改变状态后，补充查询仍可失败；response 成功不能证明所有附属步骤成功。
这些只是静态源码证据，不是 CLI 所有内部路径均已观测的承诺；现有原文输出或吞错行为也不是新服务应照搬的规范。
app-server 只能记录自身实际观察到的发送、消息、退出与清理；CLI 内部未暴露的原因必须保留为未知，不能补造工具、模型或持久化步骤。

## 领域拥有错误，diagnostics 拥有诊断机制

| 责任 | 归属与边界 |
| --- | --- |
| 输入合法性、业务失败、重试/恢复/降级决策 | 对应领域 owner；同时表达实际副作用与可行动结果 |
| CLI 启停、读写、解码与原生消息关联 | 执行 adapter / 进程资源 owner；不猜测 CLI 内部业务结论 |
| JSON-RPC 校验、领域错误的安全协议映射 | 协议边界；保留领域语义，不重新决定业务结果 |
| 安全因果摘要、结构化记录、关联与查询 | 独立 `diagnostics` 模块；只统一机制，不统一业务含义 |

各领域以自身 Rust 错误/判别结果表达调用方需要区分的原因；不统一压成字符串或任意错误容器。
diagnostics 不建立全局错误字典、万能业务错误 enum、统一恢复策略或第二套 business owner。
它不持有 agent/session/run 的 canonical state，不发业务补偿命令，不以日志推导或修正终态。
领域可以复用安全投影机制，但错误分类与 public code 的映射必须在责任边界可见；不得靠集中匹配文案猜原因。
module/crate 落位由架构 owner 冻结；“独立 diagnostics 模块”不自动要求独立 crate、服务或新增遥测依赖。

## 关联标识只带适用字段

下表是语义约束，不是已批准的字段 schema；不存在、尚未建立或不适用的标识不填伪值。

| 标识 | 用途；不可替代什么 |
| --- | --- |
| `requestId` | 客户端一次协议请求/响应关联；按连接或已定义的命名空间解释，不等于执行 ID |
| trace / operation correlation | 仅在确有跨请求因果链时建立；连接启动、后续控制与清理，不强制所有操作生成全套 ID |
| `agentId` | 适用的逻辑 agent 归属；不是 CLI PID，也不是每次请求的新 ID |
| `sessionId` | 会话身份；保留原生身份及映射来源，不等于某次 run 或某个进程实例 |
| `runId` | 一次执行的归属；不承担消息身份或排序，控制请求可关联正在控制的 run |
| CLI 实例标识 | 区分每次启动的实际执行后端，包括同 session 重启；PID 仅为辅助观察，不能单独作为身份 |
| 原生 `request_id` | CLI control request/response/cancel 配对，必须带 CLI 实例作用域；不直接冒充外层 `requestId` |

一个外部请求可能产生多个原生控制请求，CLI 也可能主动发起权限请求；由 adapter 保存实际映射，不假设一对一。
重复、迟到、孤儿 response 与正常 response 分开记录；是否忽略或处理由原生协议语义决定，不能再次执行副作用。
异步任务携带自身关联上下文，不依赖全局“当前 session”；不靠时间相近、同 PID 或相同文本把并发操作拼成因果链。
消息 UUID、序列号与时间各保留其消息身份、顺序、观察时间语义，不能替代上述标识或据此推断全局顺序。

## 协议错误不能失去具体原因

- JSON-RPC 标准错误用于解析、请求结构、方法、参数及真正的内部异常；与可识别的领域业务失败分开映射。
- 领域已有的具体 stable code 与 safe data 应穿过内部调用、adapter 和协议出口，不得一律转成 `internal_error`。
- safe data 仅包含调用方行动所需的安全事实，如失败步骤、可确认的应用范围、恢复条件；不透传底层错误对象。
- 用户消息说明发生了什么、已知原因与下一步；未知就明确未知，不用一条 `failed` 掩盖所有分支。
- 预期失败由领域显式返回；未知异常保留 source/context 传到边界，再生成安全响应，不吞掉或伪装成功。
- 原生 CLI 若只有 `error` 字符串，就保留“原生控制失败”的可证实分类与安全摘要；不能凭文本发明精确业务 code。
- 未知原生 type/subtype 保留安全的类型信息与兼容性结论；不擅自当作普通业务失败、成功或崩溃。
- 请求响应失败与业务操作失败分开：操作可能已成功但响应未送达，诊断须能关联这两个事实。
- 对无可响应 ID 的畸形请求、notification 和已断开的连接，遵守协议规则；不能为补齐诊断伪造响应。
具体业务 code、safe data 形状、Rust 类型与应用错误码精确数值均为 **OPEN**，由对应 owner 与协议 owner 协同冻结。

## 错误、取消、退出与未知结果分开

| 观察 | 必须保留的区别 |
| --- | --- |
| 控制请求成功 / ACK | 只证明该控制动作的接收或返回；不是 run terminal，更不是所有清理完成 |
| 已请求 cancel / 收到取消证据 | 意图与执行结果分开；取消原因、发生阶段及后续清理仍由执行 owner 说明 |
| 非零 exit / signal 终止 | 是进程观察；保留退出事实及已有原生结果，不能反推出具体业务原因 |
| 畸形 stdout | 是 framing、JSON 或消息形状问题；不是业务失败正文，不能把原始行直接记日志 |
| EOF | 是流结束；区分正常完成后的 EOF、等待 response/terminal 时的提前结束与进程退出 |
| stderr 有内容 / 没有内容 | 仅辅助观察；既不直接证明业务失败，也不证明成功，不能作为完整错误契约 |

即使 exit 为零，没有所需 terminal 证据也不能宣称业务成功；已有结果与后续异常冲突时保留两者，不覆盖历史。
取消不是普通失败；取消请求成功也不能证明副作用未发生，终态只能依据该操作真实可得的证据。
副作用已发送、发生部分写入或提交无法确认后失联，应表达具体阶段的结果未知，不能宣称“未执行”。
结果未知不等于未知异常：前者描述副作用证据不足，后者描述失败原因未分类；不能混成一个通用 `Unknown`。
没有领域证明的幂等性、确认未执行或安全恢复条件，不得自动重发；诊断模块不能自行决定重试。
这些区分落在各操作自己的结果与转换里，不新增覆盖所有领域的泛化状态机，也不任意添加超时/重试次数。

## 因果、部分应用与清理不能丢

内部错误保留原始 source chain / cause 与操作上下文；公开响应、日志和查询只输出经过安全投影的因果摘要。
跨边界包装须保留来源与具体原因，不能只留下最外层 `Display` 文案；安全限制不等于删除整条因果链。
多步骤变更逐项保留已完成、失败、未执行及结果未知的事实；部分应用不伪装全失败或全成功，不靠一句“已回滚”覆盖。
恢复、补偿或重试失败须链接原始失败，并记录实际尝试与结果；不得把恢复失败覆盖成唯一原因。
cleanup 失败作为关联的独立结果保留，不能覆盖主失败，也不能因主操作成功而静默忽略。
需要确认的 flush、commit、stop、join、shutdown 走显式可失败路径；不能依赖 `Drop` 给出成功承诺。
取消/断连时按实际所有权清理：释放已结束操作持有的 pending 与任务；客户端连接断开不等于取消 Run 或销毁共享 CLI。执行确已关闭时回收进程资源；未能确认释放就记录事实与后续处置责任。
若 native transcript 需要补齐消息配对，只由执行/协议 owner 依原生规则处理，diagnostics 不合成会话内容。

## 安全记录与查询

- 日志、遥测、诊断查询不保存原 prompt、原始 tool 输入、完整请求/响应体、原始 thinking，也不复制 native transcript。
- secret、token、Authorization、API key、password，以及可携密的 argv/environment、URL、私密路径、provider body 和 backtrace 不进入公开诊断面。
- stderr、stdout 解析片段、source 文案和第三方错误都视为不可信敏感输入；先安全投影再记录，不以“仅 debug”豁免。
- 安全化失败只输出安全占位与失败事实，绝不回退原文；按宪法限制日志长度，截断需可辨识，具体阈值 **OPEN**。
- 只记录定位所需的命名空间/owner、操作与阶段、结果/原因、安全因果、耗时及适用关联；这是信息需求，不是字段表冻结。
- 原生 transcript 仍由 CLI 管理；仅在允许时引用安全会话/消息标识，不另建含敏感内容的“诊断 transcript”。
- 查询不能成为跨 agent/session 的泄漏入口；使用调用方已有授权边界，仅返回其可见范围，不能靠 ID 可猜测性授权。
日志等级及其分配、字段名称/必填性/编码、关联传播载体、查询接口和可见范围细则均为 **OPEN**；不在此伪造已批准 schema。

## 事件存储与诊断存储分责

业务事件表示已发生的事实，其顺序、重放与保留由事件 owner 负责；当前状态投影不能覆盖历史事件。
diagnostics 保存安全运行证据与因果检索信息，不取代事件流、状态库或原生 transcript，也不是完成结果的唯一事实源。
事件与诊断可通过适用标识关联，但不复制整份业务 payload，不让诊断查询替代业务查询。
高并发记录不能串成跨所有 CLI 的业务锁，不能要求每条流消息同步持久化完整诊断，也不能引入无界异步积压。
诊断写入/flush/查询失败必须可见且不得递归记录自身直至失控；保留原操作结果，不将观测失败冒充业务失败。
诊断缺失时不得声称“全链已记录”；需确认的持久化失败也不能静默忽略或靠无限重试掩盖。
存储介质、保留/轮转、背压、写入确认与失败报告路径均为 **OPEN**；按真实并发与可靠性需求冻结，不添加任意配额。

## 并行开发交付要求

每个操作在自己的实现/交付说明中写清：**输入分支 → 业务副作用 → 失败结果 → 清理 → 诊断证据**。
只列该操作真实分支与具体返回；覆盖校验、原生交互、状态/持久化、响应发送及恢复/清理的实际失败，不生成通用长模板。
例如发送 interrupt：目标 run 已结束/仍活动 → 是否已向 CLI 发出 → 控制失败或仅 ACK → 等待实际结束与清理证据 → 关联两层请求及 CLI 实例。
领域 agent 交付自身错误与恢复决策；adapter agent 交付真实 CLI 观察与映射；协议 agent 保住具体安全返回；diagnostics agent 只实现共享机制。
必须区分源码已证实、实现目标、待冻结 **OPEN** 与 CLI 内部未观测；不得用日志存在代替业务结果证明。
文档本身不扩大实现授权；本次生产实现依据用户后续授权与 [共享契约](contracts.md) 执行。未经明确要求仍不新增测试或临时脚本，不读取本机凭据或真实调用外部模型/账号。
