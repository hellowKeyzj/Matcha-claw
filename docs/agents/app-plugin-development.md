# Matcha 插件开发 SOP 与 Commerce 复盘

适用读者：在 Matcha 中制作插件的 Agent、独立插件开发者，以及维护 SDK／制作 Skill 的工程师。

## 1. 目标与唯一入口

将可复用的工程、工具、设计和交付判断沉淀为一套标准，让不同领域的插件可独立开发、独立分发、独立使用；不把每个插件变成宿主工程，也不把复杂业务降低成一次性脚本。

**规范执行入口是 [app-plugin-create](../../resources/skills/preinstalled-skill-sources/app-plugin-create/SKILL.md)。** 本文解释其来源、执行阶段和复盘证据，不是另一套覆盖 Skill 的开发协议。实际 SDK 包内 README／公共声明决定可用接口、命令和平台规则；不能拿本文或历史示例替代当前合同。

```text
用户任务 → 独立插件工程 → 同一业务 owner → 构建／验包 → 真实预览
                               ↑ UI／模型工具             ↓ 按意图安装
                         私有存储／外部适配          兼容电脑上的独立插件
宿主：生命周期、公开能力、安装与可信确认，不解释插件专属业务
```

统一的是质量底线，不是所有插件的文件树、视觉模板、数据库或工具数量。规模扩大后应复用 SDK、构建／验包和可运行验收方法，而不是靠每个插件修改宿主、复制框架或增加审查文档。

## 2. 从结果到交付的 SOP

| 阶段 | 必要动作 | 退出依据 |
| --- | --- | --- |
| 需求校准 | 逐项对齐用户任务、完成判据与真实依赖；多步骤任务在已有记录维护实现状态及验证证据／缺口 | 原需求都有去向，删减／延期已获同意，不以页面／函数替代任务 |
| 能力与独立性 | 选 reader／connector／application 及所需后台；从实际 SDK 核能力，独立目录管理依赖 | 不需要宿主源码或根锁文件；真实能力缺口单列，不默认改宿主 |
| 业务与合同 | 必要时冻结 owner、状态、公开参数／结果及不变量，区分业务事实与 UI 投影 | UI 和工具指向同一业务语义；复杂度与任务相称 |
| 工具与交互 | 按领域任务设计工具，按用户任务组织界面；明确高影响动作与人类决定 | 工具能选对、字段能填对、操作影响看得全；不是只看数量和短文案 |
| 实现 | 规则与 I/O 分开，按业务职责静态组合，完成四语／主题／键盘；必要时独占并发 | 无重复 owner、临时桥或未来框架；关键状态和资源归属明确 |
| 检查与工件 | 现有类型／lint／schema 检查，canonical build／pack，核真实 ZIP 及运行依赖 | 当前源码对应明确版本／digest；秘密、数据与开发路径不入包 |
| 实际使用 | 从真实入口逐项执行约定任务，核产物、回执及涉及的连续操作、冲突恢复和重开 | 每项结论有对应证据；一条流程成功不抵其余任务，缺条件明确未验 |
| 安装／分发 | 按用户意图安装精确 digest 或交独立包；核正式运行与清理 | 不依赖 watcher；兼容要求／外部配置清楚；不暗自发布或覆盖旧安装 |

阶段是检查点，不是每步向用户汇报或增加确认。微型 reader 可以一次完成；复杂业务先尽早跑通一条真实纵向流程，识别 SDK、运行时和外部服务的关键缺口，再按已冻结边界扩展其余任务。一条流程是及早发现问题的方法，不是缩小交付范围的理由；不必为每阶段建文档。

### 最小工程组织

入口、合同、领域规则／I/O、UI 是责任，不是必须创建的目录。比如一款有持久业务的 TypeScript application 可以使用：

```text
manifest.json / app-plugin.build.json / package.json / 插件自身锁文件
src/activate.ts        注册、事件、收尾
src/contracts.ts       公开请求／结果与确需共享的领域类型
src/<业务模块>/        规则、持久事实及外部适配，按真实职责划分
src/ui/                按任务组织的页面、语义样式、四语言
README.md              使用、构建、兼容与外部配置
```

无后台 reader 不造这些模块；无需持久状态就不引入数据库；只有一个操作不造通用 dispatcher。工程可以与宿主同仓，但这必须是明确的仓库选择，不能成为从生产版 Matcha 制作插件的先决条件。分发包不得依赖仓库相对路径。

## 3. 质量判据

### 用户任务完成度

交付前执行 canonical Skill 内联的六项检查：范围完整、流程闭合、依赖落地、操作可恢复、界面可用、证据对应结论。检查表不是要求所有插件增加发送、数据库、审批或自动化；只按约定任务判断。多步骤任务在已有记录使用一张简表，微型任务直接核对即可。

以下是 Commerce 的事实示例，不是未来插件的模板或本轮新增验收成绩：

| 用户任务 | 完成判据 | 真实依赖 | 实现状态 | 验证证据／缺口 |
| --- | --- | --- | --- | --- |
| 报告发邮箱 | 指定报告经确认后发送并记录结果，最终送达另核 | SMTP、凭据、发送授权、正式确认入口 | 已实现 | 本地SMTP协议已验，正式Host确认与真实邮箱未验 |
| 定时生成日报 | 到时自动运行并保存报告 | 调度与运行环境 | 未实现 | 无，手动生成不能替代 |

接口和界面存在不等于任务完成，适配器存在不等于外部服务已接通。缺凭据或授权不要求越权验证，但不能用“未验”掩盖未实现，也不能把已实现未验说成已验证可用。约定任务有缺口时，在授权与资源边界内继续解决；确缺输入／权限则报告阻塞，不能以填写状态表替代交付。

### 工程与状态

- 业务模块单写自己的事实，UI 和模型工具不重复规则；外部网关是适配边界，不是“已接通厂商”的代称。
- 确定性指标／金额／日期按业务规则计算和校验，模型仅做有依据的生成、分析或提取。模型返回先结构校验，再核语义与当前事实。
- 对版本敏感的编辑用完整内容与观察到的 revision 共同作为基线，保存采用返回事实，外部更新不悄悄覆写草稿；实际核连续保存与冲突后载入再保存，不只核旧写入被拒。审批确认后在业务 owner 复核，不能由外围自动补“当前版本”掩盖调用方未核对。
- 会产生费用或不可逆副作用的执行与准备分开。只有真实合同要求时才引入 claim／请求标识／回执／恢复；按实际执行阶段判断确定未提交、失败或未知，不把取消一律判失败或未知，不能盲重试或重建请求。
- 敏感资料留在必要私有边界；公开投影、模型输入和日志遵守各自最小需要。可信本地后台不是 OS 沙箱，app-only 不是人工批准，客户 ID 不是授权。
- 资源在取得它的 owner 中清理，disposer 保留已注册的资源引用；不能在外层对象销毁后重新访问 getter。未经证明归属不杀进程、不抢 profile 锁。

### 后台执行与持久待决定

需要指定 Agent 或团队时，按当前 SDK 的 `context.execution` 公共合同选择显式目标；原 Sessions／Organization 继续拥有原生执行与权限，插件保存业务引用及结果。`models.generateText` 不是 Agent，`compose` 不是发送，新会话也不是独立工作区或 OS 沙箱。SDK 1.1 的执行与 `background:true` 需要兼容宿主；开发后台明确不可用，不能为预览加旁路。普通插件仍独立构建，不因此每次重编宿主。

插件自行保存步骤、原请求标识、精确审批内容和依据，等待人工时释放执行位；重开后普通工具复用可信确认，再原子核版本并消费。自动授权必须明确范围、预算、目标及期限，配置变化失效；未知外发不重派。应用退出／睡眠时不承诺运行，恢复由业务 owner 负责。操作受理、run 终态、完整产物和真实平台回执分别验证，不能以模型自述替代平台读回。

### 工具、字段与提示词

判断一个工具是否写好，依次看：Agent 何时选它、每个 action 的影响、参数从哪里取得、成功／未知结果如何读取。不能把内部方法表等同于模型工具目录。

相关动作可以分组，不同风险或领域不强合；独立危险动作有清晰入口，UI 辅助工具按实际 SDK 声明可见性。工具名须在整套目录中可区分，不把“上千插件”变成上千个无上下文的 `save`／`run`。这不授权改造宿主工具发现机制。

| 内容 | 应说明什么 | 避免什么 |
| --- | --- | --- |
| 工具 description | 做什么、何时选择、与相邻工具的边界 | 把全部业务函数或每条字段规则堆在一段 |
| action description | 前提、改变什么、不改变什么、必要的副作用 | 只写 save／submit 同义词，或不同动作共用万能说明 |
| 字段 description | 含义、单位、数据来源、省略／null／空值差别 | 复述 type／required，省略关键单位或默认语义 |
| 复杂指令 | 输入角色、修改范围、必须保留的内容、输出要求 | 一律压短，或在各层重复同一套保护话术 |
| 返回说明 | 实际对象结构及成功／未知状态 | 用概念名代替真实返回位置 |

Commerce 的纠偏例子：

- 规则 `instruction` 应是“由原始反馈支持、适用所选类别的可复用运营要求”，不能套用“修改营销文案”。
- `language` 应分别说明“生成报告的语言”“提取规则的语言”“人工确认弹窗的语言”，不能统一混写 Output/confirmation。
- `audience` 的省略表示保留、空数组表示清空，这比再写一次“数组”重要。
- 交付返回 `{report}`，回执位于 `report.delivery`；不是直接返回 `report.delivery`。
- 审批会返回新 revision，后续交付使用这个真实返回值，不猜旧值。

分支 schema 必须由真实校验器验证。使用根 object＋oneOf 且字段只定义在分支时，不在根误加 additionalProperties:false；每个分支自己闭合。不要为缩短 schema 临时写一套生成器或放宽成 args:any。校验器接受不等于模型会选对；工具选择、参数正确率和总 token 要在获授权的真实任务评估中另验。

### 视觉与交互

- 任务决定信息架构：编辑器、画布、表格、列表详情和表单各有适用范围。Commerce 五页不是下一款插件的模板。
- 清爽不等于“破产版”：必要信息与功能不能删。用层次、分组、排版、对齐和主次动作降低认知成本，不靠空白、空指标或卡片墙装精致。
- 多类设置按任务进入，避免完整表单纵向堆叠；次要细节按需展开，但作决定需要的正文、影响对象、费用及风险必须完整可读。标题够用就删副标题，重复提示只留一处，短文案不加句号，输入要求就近显示。空态给下一步，示例显式加载并持续标记。
- 四语及无障碍标签在写界面时完成；按宿主主题合同使用语义变量，不另外抢主题事实源。不同插件可保留自己的视觉特征，不能变成千个同款后台。
- 宽页面和聊天窄容器都要实际检查；可见焦点、键盘路径、对比度、表单语义和减少动态效果不能省。
- 数据图应服务比较、趋势或查数，含单位、来源和可核查数据；不能把图表数量当设计水平。
- 优化完整可用而不是空壳首屏。避免初始化挂载大量隐藏表格、重复订阅／读取、陈旧回包、未释放对象 URL；是否顺滑须靠真实呈现验证。

### 依赖与分发

| 依赖类别 | 交付责任 |
| --- | --- |
| 开发工具 | 开发电脑安装并锁定，不要求使用方装 pnpm、tsc 或宿主源码 |
| UI／纯 JS 依赖 | 用 SDK 构建；核实际产物，不能只因 package.json 有依赖就说已带齐 |
| Node 内置能力 | 核接收方 Matcha 的真实运行时支持，不能拿开发电脑 Node 版本代替 |
| Python | 按 SDK 的解释器／锁文件合同交付；首用可能下载，不承诺默认离线 |
| Rust／native | 真实目标平台／架构工件及必需库，兼容与许可清楚，不只改 manifest 标签 |
| 模型／账号／网关 | 使用方配置或授权的外部条件，不打包秘密；接口可调用不等于服务已部署 |

“可分发”至少包含合法工件和明确兼容条件；声称“其他电脑已验证可用”还需要无源码、无开发依赖的真实兼容环境验证。不强迫使用者复制仓库，不因为插件在同仓构建就重编宿主。

## 4. Commerce 开发复盘：保留什么、纠正什么

日期：2026-11-04。下列是这次开发的证据和学习，不把历史检查当未来插件的通过成绩。原始记录见 [verification.md](../../.scratch/commerce-app-20261104/verification.md)。

| 实际过程／问题 | 证据与判断 | 沉淀到 Skill 的改变 |
| --- | --- | --- |
| 用户要求全部业务集中在插件，同时保持高工程质量 | [runtime](../../apps/commerce/src/runtime.ts) 静态组合领域模块；[contracts](../../apps/commerce/src/contracts.ts) 与 UI／注册入口共用业务合同 | 业务 owner 留插件，宿主只提供通用能力；不因插件小而乱写，也不造第二业务平台 |
| 最初公开20个工具，内部方法几乎逐个外露 | [manifest](../../apps/commerce/manifest.json) 后收为领域 action 与独立派发；内部能力并未随工具数删除 | 先按 Agent 任务设计公共面，不以工具数多证明功能，也不以工具数少证明更省 token |
| 分组初稿重复说明增大体积，随后又过度压缩字段语义 | 验证记录保留实际尺寸变化；后续 description 修正用去说明后的相同 hash 证明接口未改 | 直接、充分、不省条件、不重复；长度是结果，不是优化目标 |
| 用户两次问工具说明，助手转去 Design 图片提示词 | 验证记录“工具与字段说明修正”记录对象误解；图片顺序猜测经输入校验反证后撤回 | 先对齐当前指代和合法输入，不为错误诊断加补丁，不把相邻例子当任务 |
| 公开报告交付出现自动取当前版本的旁路 | [runtime](../../apps/commerce/src/runtime.ts) 与 [activate](../../apps/commerce/src/activate.ts) 最终只保显式 revision 的报告交付入口 | 一个语义一条路径，旧入口在当前块退出，不靠外围重复校验掩盖 owner 分裂 |
| 可信确认超出当时宿主公开能力，新增中性 SDK 能力 | [SDK README](../../sdk/app-plugins/README.md) 与实际 requestConfirmation 合同；插件 ZIP 不含宿主实现 | 新增插件不默认改宿主；真正平台缺口单独授权、标兼容要求，不偷偷塞业务桥 |
| 同仓 workspace 锁记录让用户担心每开发一款都要重编宿主 | 插件 package 使用仓库相对 SDK；内置与 workspace 本是不同机制 | 默认独立工程／锁文件／公开 SDK；是否内置、是否宿主升级分别解释 |
| 真实退出暴露清理顺序缺陷 | 首轮桌面日志定位确认 IPC disposer 在窗口销毁后重新取 webContents；修为持有原资源引用 | 资源 owner 和收尾必须真实验证，编译／局部回放不能代正常应用退出 |
| driver 选择器失败、后来又被磁盘守卫中止 | 第一次 exit1 的定位失败与退出问题分别记录；第二次 exit125 尚未观察到人工决定 | 先界定产品／验证工具／环境失败，不能据选择器或守卫失败改业务或假报通过 |
| 隐藏完整数据表影响初始渲染 | [Overview](../../apps/commerce/src/ui/Overview.tsx) 改按展开挂载；只有合成渲染边界测量 | 消除真实无用工作，保留完整数据；局部测量不冒充浏览器完整 ready |
| 最新措辞只改源码，旧 ZIP 未重打 | 验证记录明确最新说明不在历史包中 | 所有运行成绩和 digest 绑定具体工件，源码改过就不能继续称旧包是最新版 |
| 局部操作能力被表述为接近完整S1–S4流水线 | 用户质疑后确认定时、策略分流等仍缺失；2.1.0新增SMTP邮件并不补齐这些缺口 | 逐项核用户任务，实现与验证分开记录；手动操作不抵自动流程，延期须明确同意 |
| Team控制接口齐全，但真实原生公开结果固定空消息 | [本轮记录](../../.scratch/app-plugin-sdk-20261104/implementation.md)：旧模拟提供了native没有的正文；1.2已补原terminal／store／public分页与Commerce消费，原生库编译及合成消费者通过，真实执行仍未验 | SDK结果能力必须核producer→持久化→公开读取→业务消费；unavailable只防假成功，不代表缺能力已补；mock不得超前于native生产合同 |
